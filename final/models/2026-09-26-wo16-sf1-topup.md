## 1. Pre-registration (written and committed BEFORE any live data write)

### Problem

`data/sharadar/sf1_fundamentals.parquet` and `sf1_shares.csv` end at filings
dated 2026-09-08 (pulled 09-08/09; the 09-08 day itself is partial, 5 rows).
No Retrain step refreshes them, so every panel date after 09-08 carries the
last filing <= 09-08 forward: point-in-time correct but stale through the Q3
filing season. WO-14's `refresh_working_panel.py` only reads the frozen file.

### Who reads what (determined from code, integration d7d257d)

| file | live readers | dimensions |
|---|---|---|
| `sf1_fundamentals.parquet` | `build_features_fundamentals_sharadar.py` (market_cap = close x sharesbas, the 14 ratios), `reset2026/quality_factors.py` (gross_profitability, accruals, asset_growth), `sweep/events.py` (days_to_next_filing_seasonal, ARQ filing dates), `build_new_factors.load_sf1_facts` via `prediction_ledger.compute_leverage` (ext leverage, at record time) | ARQ, ARY only |

Unique key, both files: (`ticker`, `dimension`, `date`), where `date` is the
SF1 datekey (filing date). 0 duplicates on disk; both files are sorted by
(ticker, date, dimension). The original pull scripts dedup on exactly this key
(first row seen wins).

### What the top-up does (`final/src/reset2026/sf1_topup.py`)

- Pulls only the incremental range, ARQ and ARY, from the same Sharadar
  `fundamentals` endpoint the original scripts used:
  (a) `date >= max(date on disk) - 5 days`, and
  (b) `lastupdated >= max(date on disk) - 2 days` (catches late-added keys and
  vendor revisions of old keys). Expected ~4-6 calls. If the incremental range
  needs more than 20 pages the script stops (a bulk pull is out of scope).
- **Append-only.** Every row already on disk stays byte-identical (values,
  dtypes, arrow schema; for the CSV, the original lines appear unchanged and in
  the same order). New keys are inserted and the file is stable-re-sorted by
  (ticker, date, dimension), the order both files already have, because the
  readers' `drop_duplicates(keep="last")` on (ticker, filed_date) relies on ARQ
  preceding ARY. A fresh row for an EXISTING key with different values (a
  restatement / vendor revision) is NOT applied: it is logged to
  `data/sharadar/sf1_topup_restatements.csv` (key, column, old, new, seen_at),
  deduplicated so a rerun adds nothing.
- `sf1_shares.csv` gets the same treatment from the same pull (sharesbas kept
  as the API's raw string, rows with empty sharesbas skipped, as the original
  script did).
- Every appended key is logged to `data/sharadar/sf1_topup_appended.csv`
  (file, ticker, dimension, date, appended_at). The panel refresh uses it to
  tell an explained fundamentals change from a bug.
- Atomic: temp file -> validate (old rows identical, key unique, schema equal,
  sorted) -> `os.replace`. Before the first replace, dated backups
  `sf1_fundamentals_through_2026-09-08.parquet` / `sf1_shares_through_2026-09-08.csv`
  (hard links; refuses to overwrite an existing backup).
- Idempotent: a second run appends nothing and leaves both files' sha256 unchanged.

### Wiring

`refresh_working_panel.py` runs the top-up first by default (before its
up-to-date early return, so SF1 stays fresh even on a no-op day), and
`--no-sf1-topup` skips it. The top-up never runs under `--check` or `--no-swap`.
No key -> the refresh fails (exit 1, nothing written), as the insider step does.
This changes WO-14's "a no-op run writes nothing" contract to "a no-op run
writes nothing except the SF1 top-up". No app change: Retrain ALL already calls
`refresh_working_panel.py --through latest --record-weekly`, and its
`_sharadar_key_preflight` guarantees the key is in the environment.

### Acceptance rule change (Gabe's approved exception, 2026-09-26)

Gabe, 2026-09-26: **"fundamentals may change on rows < 7 days old."**
Implemented exactly as:

- `window_start = run date - 7 calendar days` (run date = the local date the
  refresh runs; 2026-09-26 -> window_start 2026-09-19).
- Fundamental-derived panel columns: `market_cap`, `net_issuance_pct`,
  `days_to_next_filing_seasonal`, `gross_profitability`, `accruals`,
  `asset_growth`.
- Panel rows with `date >= window_start`: those columns MAY take the
  recomputed value. Every changed (ticker, date, column, old, new) is listed in
  `out/reset2026/downcap_v2/sf1_window_changes.csv`.
- Panel rows with `date < window_start`: must stay bit-identical. If the
  recomputed value differs AND the difference is explained (the ticker has an
  appended SF1 key with datekey <= the row date), the STORED value is kept (it
  is the point-in-time record of what was known) and the case is logged in
  `out/reset2026/downcap_v2/sf1_kept_stored.csv`. An unexplained difference
  stays a hard failure (exit 1), exactly as in WO-14.
- Revised tickers (WO-14's full-history replace path): on rows before
  window_start that the stored panel has, the SF1-only columns are restored to
  the stored values where explained (logged the same way). `market_cap` is
  restored only where the stored close equals the recomputed close; where the
  close itself was revised it keeps the recomputed value (logged as `mixed`).
- `eligible_*` flags: kept as stored everywhere (WO-14 rule unchanged); the
  number that would flip inside the window is reported.
- Non-fundamental columns: WO-14 rules unchanged (labels only NaN -> value,
  everything else identical).
- Forward-ledger CSVs (`prediction_ledger_v3/ext/hedge`, and `_sue` if present)
  and their sidecars (`ledger_record_log.csv`, `ledger_record_annotations.csv`,
  `ledger_panel_manifest.json`) must be byte-identical before/after (sha256).
  This WO writes no ledger records. Note: the W39 record (panel_date 09-24)
  lies inside the window, so after the next real refresh the panel's 09-24
  fundamentals may no longer reproduce the recorded 09-24 scores; the ledger
  CSV itself is the record and is never rewritten.

### Named checks (pre-registered)

1. SF1 max datekey before/after, rows appended per file, restatements logged.
2. >= 3 real companies with a 10-Q/10-K filed between 2026-09-09 and today,
   chosen from the rows actually pulled: the new SF1 row exists with
   datekey = the EDGAR filing date (EDGAR submissions JSON if reachable,
   otherwise stated as unverified), and the panel's gross_profitability for
   that ticker steps on the first panel date >= datekey and never before.
   Filers with datekey >= window_start are used for the "steps at datekey"
   check; for one earlier filer both views are shown (the recomputed part
   steps at its datekey; the spliced panel keeps the stored values and logs
   them).
3. One ticker with no new filing: its panel rows are unchanged.
4. Ledger hashes unchanged; second top-up run: same sha256 (idempotence).
5. Real run: top-up, `refresh_working_panel.py --through latest --check`, and
   a real refresh WITHOUT `--record-weekly` only if new SEP data exists
   (otherwise the panel check runs as `--no-swap`, which may proceed at
   through == old_end when appended SF1 keys touch the window; temps deleted
   afterwards).

Kill / BLOCKED: needs a bulk pull, key or network unreachable, or a
permission denial. Iteration cap: 3 fix-and-rerun cycles.
