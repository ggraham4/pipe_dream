## 1. Live `seas`

- **Definition.** The WO-18 definition, unchanged
  (`final/src/seasonality/build_seas.py`; doc `2026-09-26-seasonality-screen.md`):
  - Target month T = t + 28 calendar days.
  - r(i, y, m) = ME(y, m) / ME(y, m-1) - 1, where ME is the last finite,
    positive SEP `closeadj` in the calendar month.
  - seas = the mean of r over y = Y-10..Y-1, requiring at least 5 finite
    years.
  - Sign +1.
- **Where it runs.** `final/src/seasonality/seas_live.py` computes seas
  **at score time**, reading only the 20 SEP month files a date needs from
  `data/sharadar/panel/stocks/`. These are the same files the WO-14 refresh
  tops up. It imports its constants from `build_seas.py`.
  - The panel is untouched: no column is added and no stored row changes.
  - The refresh is unchanged, so WO-14 overlap acceptance is unaffected.
  - The scoring scripts run in every Retrain, so every Retrain recomputes
    seas.
- **PIT.**
  - The last month used is (Y-1, m), and its last calendar day must be
    earlier than t (asserted).
  - Every SEP row read must be dated earlier than t (asserted).
- **Selftest** (`seas_live.py selftest`, run against WO-18's
  `seas_factor_v2.parquet`).
  - Dates: 2019-01-02, 03-15, 06-03, 10-28 and 12-31. These cover a target
    month equal to t's month, the next month, and a year boundary
    (12-31 targets 2020-01).
  - All panel tickers on each date (3,954 to 3,984), and the NaN pattern,
    `seas_nyears` and `target_ym` all match.
  - Maximum absolute difference: **0.0**. **PASS** (tolerance 1e-9).
  - `build_seas.py` was rerun in this worktree, and its output equals
    WO-18's file exactly (`DataFrame.equals`).
- **AAPL hand check** (`seas_live.py handcheck AAPL`). This is independent
  loop code on raw SEP.
  - t = 2026-09-25, so the target is 2026-10, using years 2016 to 2025.
  - Hand result 0.0318379 equals live 0.0318379, difference 0.0. **PASS**.
  - One year as a sanity check: October 2020 = 112.245 to 105.509, which is
    -6.0%.
- **Live coverage.** v3's cap150 rows on 2026-09-24: 86.3%. Eligible cap2000
  names on 2026-09-25: 90.3%. The in-era cap150 range was 0.76 to 0.85.
- **Failure behaviour.** If a SEP month file is missing, or seas coverage on
  the scored cross-section falls below 60%, the scoring script **fails**.
  Neither script ever falls back to the pre-seas model under the new label.
- **LANDMINE: split/dividend basis.** `closeadj` is rebased to its pull
  date, so both months of one return must come from the same pull.
  - Today every month a live date needs (at most 2025-12) comes from the one
    2026-09-09 bulk pull. `2026-09.parquet` was re-pulled on 2026-09-26.
  - Around 2027-08 (target month 2027-09, using the 2026-08 to 2026-09
    return), live seas will start mixing pulls.
  - `seas_live` reports the file-mtime spread of the files it uses as
    `basis_flag` in both metas.
  - Before that date, a fix is needed: either re-pull the recent months, or
    splice as `build_seas.splice_month_ends` does.

## 4. Forward record (pre-registered)

**Ledgers.** `final/src/seasonality/seas_forward.py` writes two ledgers,
both only through `record_weekly.py`, after v3 and SUE:

| ledger | rows | new score | paired against |
|---|---|---|---|
| `prediction_ledger_seas.csv` | v3's cap150 rows, same order; icw8 must equal v3's `ic_weighted_score` to 1e-12 | `icw9_seas_score` | `icw8_score` |
| `prediction_ledger_blend_seas.csv` | every cap2000 name both blend legs score (`current_signal_blend.blend_scores_at`) | `blend_seas10_score` | `blend_prev9_score` |

**Existing ledgers.** v3, ext, hedge and sue are untouched and stay
byte-identical. Their weekly records continue as before.

**Record dates.** Each side ledger records every v3 panel date **after
2026-09-24** that has no record in that ledger. That means W40 onward, one
per ISO week, following v3. 2026-09-18 and 2026-09-24 are not backfilled:
their records would be `recorded_late` and never counted anyway.

**Guards.**
- Duplicate-date guard.
- Blindness guard: refuse if any eligible name has a matured
  `forward_return_tradable_40`.
- Pairing with v3 (seas ledger only).
- Seas coverage of at least 60%.
- Manifest entry.
- Byte-prefix checks in `record_weekly`, which now also cover both new
  ledgers and `ledger_seas_guard_log.csv`.
- One record per ISO week.

**Isolation (as in WO-15 Addendum A, per ledger).** Any failure in plan,
preflight, record or the sidecar step skips only that ledger's record for
that date. It is logged to `out/reset2026/ledger_seas_guard_log.csv`. It never
stops v3, ext, hedge, sue, or the other side ledger. If a record step raises
after appending, the run reports the half-written record at the end, after
hedge has recorded.

**Counted dates.** These follow the WO-15 rule, applied to each ledger
separately:
- Excluded: `recorded_late` records (more than 7 days after `panel_date`)
  and `incomplete_week` records.
- Seas coverage on the ledger's rows must be at least **0.70**.
- Greedy selection: the first eligible record counts, and each next counted
  date is the first eligible record at least **40 trading days** after the
  previous one. The calendar is IWM_live, which agrees with the working
  panel.

**Primary statistic (per ledger).** On each counted date, after its 40-day
label matures, compute
`gain_raw = Spearman(new score, realized) − Spearman(previous score, realized)`,
where realized is `forward_return_tradable_40` from the working panel.

**Read once, at the 6th matured counted date.**
- Mean `gain_raw` over the first 6 counted dates **> 0**: CONSISTENT. The
  seas version stays, and this is reported to Gabe.
- Mean **≤ 0**: a **DEMOTION QUESTION to Gabe**. Nothing is demoted
  automatically.
- Descriptive only, never gates: `gain_beta_adj` (beta_252 × SPY forward 40)
  and `gain_sector_both`.
- `seas_forward.py status` prints the state. `score` runs only on matured
  dates.

## Addendum A (2026-09-27, before any record)

Found in review after the first commit (999db67) and before any record. Sections 1 to 6 are unchanged.

- **Row-count guard.** In `seas_forward.py`, `build_seas_rows` and `build_blend_rows` now raise (the date is **skipped**, isolated and logged) when a date's row set has fewer than `MIN_ROWS = 100` rows.
  - Before this, an empty `blend_scores_at` result would be appended as a 0-row record. The cause could be a missing `pit_universe` entry, or q75 scoring nothing.
  - `recorded_weeks` would never see that record. `record_weekly`'s final "weeks still missing" check would then return rc 1, after v3/ext/hedge had recorded. That breaks isolation.
  - The fix is tested by the 8th isolation mode, `blend_empty`.
- `seas_forward.py selftest` now creates `final/out/seasonality/` before saving its JSON, so it works in the main checkout.
- The renamed hold-out keys (`icw8_holdout_*` in `current_signal_composite_meta.json`'s `backtest_summary`) are read by nothing in `final/app` (grep: only a `.bak` file, reading a different top-level key). No compatibility alias was added.
